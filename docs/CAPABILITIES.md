# Detection coverage and verification guide

No URL scanner can discover every security issue. The public scan observes anonymous HTTP responses; the local source command looks for bounded patterns. Neither infers database policies, infrastructure, hidden routes or authenticated behavior with certainty. The table maps the supplied examples to implemented checks and the review needed to confirm them.

| Issue class | Public URL scan | Local source review | How to confirm safely |
| --- | --- | --- | --- |
| PDF renderer authentication, raw HTML, SSRF/local-file access | Cannot establish backend rendering behavior; does not send render jobs | Flags browser content/navigation patterns, disabled sandbox and missing visible controls | Inspect every entry point, auth middleware, template flow, browser context interception, mounts, actual sandbox state and network egress in isolated staging |
| JS-readable Supabase tokens | Inspects Set-Cookie attributes on anonymous responses; cannot see cookies written later by scripts | Flags document.cookie assignment near authentication patterns | Inspect the session architecture and actual browser storage; test login/refresh and XSS defenses with controlled accounts |
| Password-reset enumeration | Not tested: sending reset requests can trigger mail and disclose users | Flags explicit unknown-account messages in reset routes | Compare response status/body/timing for controlled registered and unregistered staging accounts; verify quotas |
| Missing environment documentation | Not accessible from a public URL | Compares process.env.NAME references with example-file variable names | Build a clean environment from the examples, distinguish optional and required settings, document server-only secrets |
| Email verification bypass | Cannot prove account changes without authorized stateful tests | Flags direct verification updates without recognized proof validation in verify-email routes | Review token/OTP validation, purpose, account binding, expiry and single use; test missing/invalid/expired/replayed proof with disposable staging users |
| Browser-process exhaustion | No load test or job submission | Flags browser launches without visible queue/pool/semaphore patterns | Review platform and worker limits; load-test staging within agreed budgets; confirm cleanup and rejection behavior |
| Container runs as root | Cannot inspect deployment image | Reviews the final Dockerfile stage's USER instruction | Inspect final image metadata and run id in staging; base images may supply a non-root default |
| Role accepted during public signup | Cannot establish privilege without creating/altering accounts | Flags role assignments from request-like values in signup/register routes | Use a disposable staging account, inspect stored role and effective authorization, review privilege changes and database policies |
| Missing/weak HTTP security headers | Checks live headers, with context-specific severity and repair steps | No inference from framework config alone; middleware/CDN may supply headers | Inspect public responses across important routes, test a policy in report-only mode where appropriate and verify browser behavior |
| Public email relay/HTML injection | Does not send email or probe arbitrary recipients | Reviews visible mail authorization, rate controls and template escaping patterns | Use a staging mail sink, trusted recipient records, validated links and controlled escaping tests |
| Vulnerable Next.js, nodemailer or other npm package | Cannot reliably infer installed dependency versions from a website | `--npm-audit` queries advisories for existing npm lockfiles | Review actual production dependency paths and prerequisites, apply compatible patches, test and repeat the audit |
| Public privileged keys/private keys/webhooks | Searches fetched text for known patterns, including service-role JWT claims; redacts matches | Does not harvest or report source secret values | Rotate confirmed live credentials at the provider, inspect logs, remove public copies/caches; never validate by using exposed credentials |
| Insecure password submission | Examines HTML form method, page transport and action scheme | No general source taint analysis | Confirm network behavior in developer tools; check POST bodies and HTTPS at every hop |
| Missing CSRF form field | Low-confidence prompt for POST forms only | No complete CSRF analysis | Verify backend tokens, Origin/Fetch Metadata controls and session cookies; a field alone proves nothing |
| Mixed HTTP content | Examines static HTML resource references | No CSS/JavaScript runtime evaluation | Inspect browser network activity; account for upgrades, CSP and browser blocking |
| Database errors/directory listings | Finds recognizable response text, does not call it SQL injection or confirmed private-file exposure | No query/dataflow analysis | Reproduce using controlled inputs in staging and review server error/index settings |
| Wildcard CORS | Low-severity review prompt for anonymous public reads | No complete origin validation analysis | Public resources may intentionally allow `*`; inspect credentialed/private endpoints and server authorization separately |

## Important distinctions

- **Severity is potential impact, not certainty.** Critical source patterns need careful confirmation; lower-confidence findings explicitly state the unknowns. Labels are not automatic CVSS scores.
- **Supabase SSR is not automatic HttpOnly storage.** Browser-managed sessions may need token access. Use a server-only/backend-for-frontend design when HttpOnly sessions fit the product; otherwise use the supported SSR flow and strong XSS defenses. See [Supabase's cookie guidance](https://supabase.com/docs/guides/troubleshooting/how-do-i-make-the-cookies-httponly-vwweFx).
- **Browser interception is one boundary.** Context-level interception is preferable to page-only routing, and [Playwright documents service-worker interception gaps](https://playwright.dev/docs/api/class-browsercontext). Block service workers where relevant, validate DNS/redirects, restrict network egress and isolate the renderer without production secrets. Authentication does not by itself make arbitrary HTML safe.
- **Proof of email ownership must be validated.** Supabase provides [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp); a request-supplied email address is not proof.
- **Public keys and public APIs can be intentional.** Supabase anon/publishable keys, JavaScript-readable preference cookies and wildcard CORS for public content should not automatically be treated as privileged credential leaks or confirmed vulnerabilities.

## Review limits

The source command scans up to 2000 eligible UTF-8 source/config files, 512 KiB per file and 10 MiB total; at most 500 findings and 100 warnings are emitted. It skips symlink files/directories, hidden directories, dependency/build folders, test/spec files, and real `.env` variants. Only `.env.example` and `.env.local.example` variable names are used for documentation comparison. It does not understand all languages, aliases, bracket environment access, control flow or cross-file security controls. When advisory lookup is enabled, at most 10 npm lockfiles are queried with a 60-second timeout each. An advisory failure is a warning, never a clean result.

The public scan does not execute JavaScript, submit forms, access authenticated routes, read source files, fuzz inputs, test IDOR/RLS, brute-force credentials, enumerate actual accounts, send email, make PDF jobs, check all TLS protocols/ciphers, or stress infrastructure. Request headers and rendered pages can vary by route, session, geography or CDN behavior. Treat the output as a starting point for a broader authorized review.
